# `tooling/tests`: the kac golden-file suite

`kac-tests` runs `kac` against deliberately broken (and deliberately clean) mini-corpora and diffs the findings against
a committed golden. It is an **integration** suite: it exercises the real rules end to end, not the C# internals. The
unit tests (`kac.tests`) and the Reqnroll behaviour specs (`kac.features`) live alongside it.
[`../README.md`](../README.md#tests) says what each layer is for.

```bash
dotnet run tooling/kac-tests.cs                 # run every scenario, fail on any mismatch
dotnet run tooling/kac-tests.cs -- clean        # run only scenarios whose name contains "clean"
dotnet run tooling/kac-tests.cs -- --update     # regenerate every golden from current kac output
```

Exit `0` when every scenario matches its golden; `1` on a mismatch, a missing golden, a golden that references a check
id `kac` no longer emits, stale generated output, or a reachable check with no fixture.

## How a scenario runs

Each `fixtures/<scenario>/` is a mini-corpus minus its schema. A `mode` file selects what is asserted, and a fixture
without one is validated. `new` is the one scenario carrying no corpus, because the command it runs creates one:

```
fixtures/
  clean/                                  # mode: validate (default)
    corpus/adrs/0001-clean-baseline.md    # the documents under test
    expected.json                         # the golden: the exact findings kac should produce
  generate/                               # mode: generate
    mode                                  # "generate"
    corpus/adrs/0001-first-decision.md    # source ADRs
    corpus/adrs.md                        # type page with the BEGIN/END GENERATED markers
    corpus/adrs/_index.md                 # committed generated output: the golden
  generate-stale/                         # mode: generate-stale
    mode                                  # "generate-stale"
    expected-stale.txt                    # files `generate --check` must report as stale
    corpus/...                            # a deliberately out-of-date _index.md
```

For each scenario the runner assembles a throwaway repo root in the system temp dir: it copies the **real**
`.schema/` in, drops the scenario's `corpus/` on top, and runs `kac` against it. The schema is copied fresh each run,
never from a committed copy. That is deliberate: the suite tests the **production** rules, so a schema change that
alters behaviour surfaces here as a diff. The temp root is not a git repo, so kac's discovery falls back to a filesystem
walk and paths stay corpus-relative: no temp path leaks into a golden.

The modes:

- **`validate`.** Run `kac validate --json`, and diff the findings against `expected.json`. Contributes to check
  coverage.
- **`generate`.** The corpus already contains the correct generated files (`adrs/_index.md` and the spliced `adrs.md`),
  and the run asserts `kac generate --check` finds them fresh (exit 0). The committed generated files *are* the golden,
  reviewable in git and regenerated by `--update`. A generator change makes the run fail until the golden is refreshed.
- **`generate-stale`.** The corpus is deliberately out of date, and the run asserts `kac generate --check` catches it
  (exit 1) and names the files listed in `expected-stale.txt`. `--update` leaves this fixture untouched.
- **`export`.** `kac export` runs over the fixture corpus. The export it wrote is committed under `expected-dist/` and
  diffed whole, file for file, so a key that appears, moves or goes fails the run. Every file in either tree is named,
  and `--update` rebuilds the committed copy. The manifest's `generatedAt` and `commit` are replaced by their own names
  on both sides, since they differ between two runs over one tree. Beside the tree, `expected-export.txt` names lines
  the run must print, `expected-files.txt` what must be there outside the export, and `expected-content.txt` the
  `<path> :: <text>` pairs, read against the emitted file, which is where those two fields are pinned. `export-type`,
  where present, names the type to pass to `--type`. The run happens twice: the second is over an output seeded with a
  file no record backs, which asserts the overwrite is delete-then-write. The temp root is not a git repository, so no
  ref resolves and no link is written. The fixture therefore pins the corpus-publishes-nowhere path, and the link forms
  belong to the unit layer, which can supply a ref.
- **`bundle`.** The fixture's `plugin/` tree is laid down as `.plugin/`, then `kac export` and `kac bundle` run over it.
  There is no committed copy of the plugin: most of one is the export, which the `export` fixture already pins file for
  file. What is asserted instead is what a bundle adds: `expected-bundle.txt` names lines the run must print, and
  `expected-files.txt` and `expected-content.txt` read the tree afterwards, the same two files `sync` and `export` use
  and with the same `!` prefix inverting a line. Beside them the runner compares the copy of the export inside the
  plugin with the export it came from, byte for byte, which is what makes a difference between the two a defect rather
  than something to interpret; `corpus-root` names where that copy landed. `export-type`, where present, names the type
  to pass to `--type`. The run happens twice, the second over a plugin seeded with a skill no component backs.
- **`new`.** `kac new --yes` runs into an empty temp folder, taking its template from this repository. Nothing is cloned
  and nothing reaches the network. Two files hold what it wrote: `expected-tree.txt` is every path the creation left,
  and `expected-descriptor.yaml` is the `.corpus.yaml` it composed. The two facts about the machine that ran it are
  replaced by their own names, since neither can be committed: the repository's path, and today's date. The file bodies
  are deliberately not asserted, because they are the template's and the template has tests of its own. The exit code is
  the third assertion and carries the most: `new` runs `validate` before it returns, so exit 0 says the corpus it
  created validates.
- **`update`.** The scenario stands its own corpus up rather than reading one, as `new` does. It runs `kac new` against
  the real template, commits, breaks the tree in two ways, and then drives the round trip: `--check` has to fail and
  name what it found, the update has to succeed, and a second `--check` has to find the corpus in step.
  `expected-check.txt` is what the first check printed, with the repository's path and the tallies taken out.

Only `validate` runs the validator directly, so a new check cannot affect the rest. `new` reaches it at one remove,
through the corpus it creates.

## Writing a scenario

1. Create `fixtures/<name>/corpus/<type>/<doc>.md` with the defects (or the valid document) you want to pin.
2. Run `dotnet run tooling/kac-tests.cs -- --update <name>` to generate `expected.json`.
3. **Read the golden.** `--update` captures whatever kac currently emits; the review step is where you confirm those are
   the findings you intended. Commit the corpus and the golden together.

Because a golden captures the **whole** findings set for its corpus, an accidental extra finding elsewhere in the corpus
shows up as a diff, which is the point. Keep scenarios coarse (one dense corpus per theme) rather than one file per
rule: each scenario is a separate `kac` process, so a file-per-rule sprawl is slower for no gain, and cross-document
rules (`id-unique`, `reciprocal`, `related-matches-section`) need related documents in one corpus anyway.

For a **generation** scenario, add a `mode` file, author the source ADRs and a type page carrying the `BEGIN/END
GENERATED` markers, then run `--update <name>`: the runner runs `kac generate` in a temp assembled from the corpus and
copies the generated files (`_index.md`, the spliced type page) back into `corpus/`. Read those files, then commit them
with the corpus.

## Coverage

On a full run the suite compares the checks exercised by the goldens against `kac checks`, the authoritative catalogue
of every rule `kac` implements. **Every reachable check must have a fixture**, or the run fails. It holds in both
directions, so a check named in a golden that the catalogue does not carry fails too, which is a rename that left a
stale golden. A check no discovered document can reach is listed as `unreachable` and excluded. Adding a new rule
therefore means adding a scenario that exercises it, or CI goes red.

**The catalogue is a property of a corpus, not of the tool.** `CheckCatalogue.For(schema)` appends each expression
rule's `(id, severity, description)` to the core checks. That is why `Commands.Checks` takes the repo root, and why a
rule declared in YAML cannot ship without a fixture any more than a C# check can.

**The gate reads ids, not branches.** `y-statement-present` reports several faults under one id: an absent block-quote,
a missing move, or a Y-statement past `max-words`. A fixture for any one of them satisfies it. A rule with more than one
way to fail needs a fixture for each, or unit tests beside its rule class for the branches a second fixture would only
duplicate.

**Standing a rule up costs more in fixtures than in schema.** A rule on a type this suite has not met yet needs that
type stood up here: a page, a template and a record. That runs to an order of magnitude more lines than the YAML
declaring the rule. That is not a cost of writing rules as data: the gate demands a fixture however a check is
implemented. It is mostly one-off, too; once a type is present, the next rule on it is a record.

### Known validator gaps surfaced by the suite

- **`type`** fires only for a document whose folder maps to no schema, but discovery excludes non-type folders, so no
  discovered document can reach it. The coverage gate lists it as `unreachable` rather than demanding a fixture for it.
