# `tooling/tests`: the kac golden-file suite

`kac.goldens` runs `kac` against deliberately broken (and deliberately clean) mini-corpora and diffs the findings
against a committed golden. It is an **integration** suite: it exercises the real rules end to end, not the C#
internals. The unit tests (`kac.tests`) and the Reqnroll behaviour specs (`kac.features`) live alongside it.
`docs/maintaining/build-test-release.md` says what each layer proves.

```bash
dotnet test --project tooling/kac.goldens                                     # every scenario and every gate
dotnet test --project tooling/kac.goldens --filter-trait "Scenario=clean"     # the scenario named clean
KAC_UPDATE_GOLDENS=1 dotnet test --project tooling/kac.goldens                # regenerate every golden from kac
```

Each scenario is one test case, named `Scenario(name: "<scenario>")`, and the scenarios run in parallel. Each gate is a
case of its own. A case fails on a mismatch, a missing golden, or stale generated output. The gates fail on a golden
that references a check id `kac` no longer emits, a reachable check with no fixture, a verb the suite never runs, a
checks table out of step with the catalogue, and a `kac` that needs a corpus to print its version or its help.

## How a scenario runs

Each `fixtures/<scenario>/` is a mini-corpus minus its schema. A `mode` file selects what is asserted, and a fixture
without one is validated. `new` is the one scenario carrying no corpus, because the command it runs creates one:

```
fixtures/
  clean/                                  # mode: validate (default)
    README.md                             # what the fixture proves
    corpus/adrs/0001-clean-baseline.md    # the documents under test
    expected.json                         # the golden: the exact findings kac should produce
  generate/                               # mode: generate
    mode                                  # "generate"
    corpus/adrs/0001-first-decision.md    # source ADRs
    corpus/adrs.md                        # type page with the BEGIN/END GENERATED markers
    corpus/adrs/_index.md                 # committed generated output: the golden
  generate-stale/                         # mode: generate-stale
    mode                                  # "generate-stale"
    expected-stale.txt                    # files `generate --check` must report as stale
    corpus/...                            # a deliberately out-of-date _index.md
```

For each scenario the runner assembles a throwaway repo root in the system temp dir: it copies the **real**
`.schema/` in, drops the scenario's `corpus/` on top, and runs `kac` against it. The schema is copied fresh each run,
never from a committed copy. That is deliberate: the suite tests the **production** rules, so a schema change that
alters behaviour surfaces here as a diff. The temp root is not a git repo, so kac's discovery falls back to a filesystem
walk and paths stay corpus-relative: no temp path leaks into a golden.

The modes:

- **`validate`.** Run `kac validate --json`, and diff the findings against `expected.json`. Contributes to check
  coverage.
- **`validate-since`.** The fixture's `base/` is committed in a repository of its own, and `corpus/` replaces it in the
  working tree. The run is `kac validate --json --since HEAD`, diffed against `expected.json` as `validate` is, and
  contributes to check coverage the same way. Only this mode's temp root is a repository.
- **`generate`.** The corpus already contains the correct generated files (`adrs/_index.md` and the spliced `adrs.md`),
  and the run asserts `kac generate --check` finds them fresh (exit 0). The committed generated files *are* the golden,
  reviewable in git and regenerated by an update. A generator change makes the run fail until the golden is refreshed.
- **`generate-stale`.** The corpus is deliberately out of date, and the run asserts `kac generate --check` catches it
  (exit 1) and names the files listed in `expected-stale.txt`. An update leaves this fixture untouched.
- **`export`.** `kac export` runs over the fixture corpus. The export it wrote is committed under `expected-dist/` and
  diffed whole, file for file, so a key that appears, moves or goes fails the run. Every file in either tree is named,
  and an update rebuilds the committed copy. The manifest's `generatedAt` and `commit` are replaced by their own names
  on both sides, since they differ between two runs over one tree. Beside the tree, `expected-export.txt` names lines
  the run must print, `expected-files.txt` what must be there outside the export, and `expected-content.txt` the
  `<path> :: <text>` pairs, read against the emitted file, which is where those two fields are pinned. `export-type`,
  where present, names the type to pass to `--type`. The run happens twice: the second is over an output seeded with a
  file no record backs, which asserts the overwrite is delete-then-write. The second run is diffed against the same
  golden, so two exports from one commit have to agree on every byte outside those two fields. The temp root is not a
  git repository, so no ref resolves and no link is written. The fixture therefore pins the corpus-publishes-nowhere
  path, and the link forms belong to the unit layer, which can supply a ref.
- **`bundle`.** The fixture's `plugin/` tree is laid down as `.plugin/`, then `kac export` and `kac bundle` run over it.
  There is no committed copy of the plugin: most of one is the export, which the `export` fixture already pins file for
  file. What is asserted instead is what a bundle adds: `expected-bundle.txt` names lines the run must print, and
  `expected-files.txt` and `expected-content.txt` read the tree afterwards, the same two files `sync` and `export` use
  and with the same `!` prefix inverting a line. Beside them the runner compares the copy of the export inside the
  plugin with the export it came from, byte for byte, which is what makes a difference between the two a defect rather
  than something to interpret; `corpus-root` names where that copy landed. `export-type`, where present, names the type
  to pass to `--type`. The run happens twice, the second over a plugin seeded with a skill no component backs.
- **`pack`.** `kac export` and then `kac pack` run over the fixture corpus, and the archive that lands is read back
  out. `expected-entries.txt` is its whole entry list, compared both ways round, so an entry that stopped travelling
  fails as loudly as one that started. `expected-nuspec.xml` is the envelope committed whole, which is the one part of
  the archive the corpus did not author. The payload is not committed a second time: every `corpus/…` entry is held
  against the export in the same temp tree, byte for byte and in both directions, because the `export` fixture already
  pins those bytes and what a pack adds is that it carried them unedited. `expected-pack.txt` names lines the run must
  print, and `expected-files.txt` reads the tree afterwards. The run happens twice, the second over a directory seeded
  with a package no run backs, and the two archives are compared byte for byte, which is what holds two packs of one
  export to one file a registry will keep forever.
- **`new`.** `kac new --yes` runs into an empty temp folder, taking its template from this repository. Nothing is cloned
  and nothing reaches the network. Two files hold what it wrote: `expected-tree.txt` is every path the creation left,
  and `expected-descriptor.yaml` is the `.corpus.yaml` it composed. The two facts about the machine that ran it are
  replaced by their own names, since neither can be committed: the repository's path, and today's date. The file bodies
  are deliberately not asserted, because they are the template's and the template has tests of its own. The exit code is
  the third assertion and carries the most: `new` runs `validate` before it returns, so exit 0 says the corpus it
  created validates.
- **`report`.** `kac report coverage` runs over the fixture corpus twice, once printing and once with `--out`. What
  the file holds is held against what the same report printed, with the `generated:` line dropped from both sides, since
  two runs a second apart disagree on the moment. A third run naming the path the second took has to exit 1, say the
  path is taken, and leave the file as it was. The file has to link the local standard by its path from `reports/`,
  link the imported policy to the page its producer published, and name the import stating no page. Nothing is
  committed as a golden: `ReportsTests` pins the report's own text, and what this adds is that the flag moves where
  the report lands and changes nothing about it.
- **`update`.** The scenario stands its own corpus up rather than reading one, as `new` does. It runs `kac new` against
  the real template, commits, breaks the tree in two ways, and then drives the round trip: `--check` has to fail and
  name what it found, the update has to succeed, and a second `--check` has to find the corpus in step.
  `expected-check.txt` is what the first check printed, with the repository's path and the tallies taken out.
- **`restore`.** `kac restore` runs once in a consumer whose `source:` is a folder beside it. The fixture's `producer/`
  is laid down as that folder, and holds a package `kac pack` built. `expected-tree.txt` lists every file the restore
  wrote under `.imports/`, and `expected-descriptor.yaml` is the `.corpus.yaml` it left, with the `resolved:` lock it
  added. The exit code is the third assertion. The package is committed, so neither file depends on the machine or the
  day of the run.

Only `validate` and `validate-since` run the validator directly, so a new check cannot affect the rest. `new` reaches
it at one remove, through the corpus it creates.

## Writing a scenario

1. Create `fixtures/<name>/corpus/<type>/<doc>.md` with the defects (or the valid document) you want to pin.
2. Run `KAC_UPDATE_GOLDENS=1 dotnet test --project tooling/kac.goldens --filter-trait "Scenario=<name>"` to generate
   `expected.json`.
3. **Read the golden.** An update captures whatever kac currently emits; the review step is where you confirm those are
   the findings you intended.
4. Write `fixtures/<name>/README.md`, saying what the fixture proves and which of its findings matter. Commit the
   corpus, the golden and the README together.

**Every fixture states in a `README.md` what it proves.** A golden records the whole findings set, and an update
rewrites it from whatever `kac` prints, so the README keeps the fixture's meaning when the golden is regenerated.
`FixtureReadmeTests` fails a fixture directory that has no `README.md`. The runner reads only the files each mode names,
so the README changes nothing a scenario asserts. Do not write a feature spec to cover a fixture. A spec exists only
where it states a behaviour a `docs/use/cli/` page promises.

Because a golden captures the **whole** findings set for its corpus, an accidental extra finding elsewhere in the corpus
shows up as a diff, which is the point. Keep scenarios coarse (one dense corpus per theme) rather than one file per
rule: each scenario is a separate `kac` process, so a file-per-rule sprawl is slower for no gain, and cross-document
rules (`id-unique`, `reciprocal`, `related-matches-section`) need related documents in one corpus anyway.

For a **generation** scenario, add a `mode` file, author the source ADRs and a type page carrying the `BEGIN/END
GENERATED` markers, then run the update for `<name>`: the runner runs `kac generate` in a temp assembled from the
corpus and copies the generated files (`_index.md`, the spliced type page) back into `corpus/`. Read those files, then
commit them with the corpus.

## Coverage

The coverage gate compares the checks exercised by the goldens against `kac checks`, the authoritative catalogue of
every rule `kac` implements. It runs every scenario first, so a run of the gate alone counts them all. **Every
reachable check must have a fixture**, or the gate fails. It holds in both
directions, so a check named in a golden that the catalogue does not carry fails too, which is a rename that left a
stale golden. A check no discovered document can reach is listed as `unreachable` and excluded. Adding a new rule
therefore means adding a scenario that exercises it, or CI goes red.

**The catalogue is a property of a corpus, not of the tool.** `CheckCatalogue.For(schema)` appends each expression
rule's `(id, severity, description)` to the core checks. That is why `Commands.Checks` takes the repo root, and why a
rule declared in YAML cannot ship without a fixture any more than a C# check can.

**The gate reads ids, not branches.** `y-statement-present` reports several faults under one id: an absent block-quote,
a missing move, or a Y-statement past `max-words`. A fixture for any one of them satisfies it. A rule with more than one
way to fail needs a fixture for each, or unit tests beside its rule class for the branches a second fixture would only
duplicate.

**Standing a rule up costs more in fixtures than in schema.** A rule on a type this suite has not met yet needs that
type stood up here: a page, a template and a record. That runs to an order of magnitude more lines than the YAML
declaring the rule. That is not a cost of writing rules as data: the gate demands a fixture however a check is
implemented. It is mostly one-off, too; once a type is present, the next rule on it is a record.

**Every verb must be run by a scenario or a gate**, or the verb gate fails and names the verb. `Suite.Run` records the
verb of each `kac` process it starts. The gate runs every scenario, then compares that set with the verbs
`kac cli xmldoc` declares. A feature file does not count. `checks` counts, because the coverage gate runs it. Each gate
prints its own tally, so neither reads as coverage of the whole tool. Adding a command therefore means adding a mode
and a fixture for it. `KAC_UPDATE_GOLDENS=1` skips this gate, because an update skips the runs of a scenario with no
golden to write.

**Every scenario is a local run.** `Suite.Run` clears each variable in `Suite.CiVariables` from every `kac` process it
starts: the two that name a CI platform, the two that name a pull request, and the two tokens. A scenario then prints
the same in CI as on your machine, and none posts a comment. The CI gates set some back with `Suite.RunUnder` and run
`kac validate` over `corpus-enums`:

* Two assert the annotation line each platform reads.
* One gives GitHub a pull request event and no token, and asserts the note saying the comment was not posted.
* One asserts that a run with none of the variables writes no annotation.

No gate posts a comment. `kac.tests/PullRequestCommentTests.cs` asserts each request a token would send.
