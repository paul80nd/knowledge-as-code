# The #987 build cases

**Two of the three build scenarios met their threshold in the plugin arm and in no none run, and one failed in every
run of both arms.**

* `loan-history` met it in 3 of 3 plugin runs and 0 of 3 none runs. Every plugin route left out loans returned more
  than two years ago, and every none route returned them all.
* `patron-reminders` met it in 3 of 3 plugin runs and 0 of 3 none runs. Every plugin session added a `Borrower` type
  or field, and every none session copied the scaffold's `RecipientEmail` and named no person.
* `second-package-unscanned` met it in 0 of 3 runs of both arms. No workflow scanned the package, and no reply raised
  `pol-TRUS.MALWARE`.

The run gives each of the three `@proposed` scenarios in [`build.feature`](../../use-cases/build.feature) its first
baseline. It writes the three cases [story #987](https://github.com/paul80nd/knowledge-as-code/issues/987) asks for, and
runs each in the plugin arm and the none arm. Each case asks for code, so each is graded on what the session wrote.

## The first runs of two cases were discarded

**`patron-reminders` and `second-package-unscanned` were run again on corrected scaffolds**, and only the reruns are
scored here. Each first run was 3 runs in each arm, and each scaffold had a fault:

* **`patron-reminders`** named its email field `BorrowerEmail` and its README said borrower. Every none session copied
  the word, so the case could not separate the arms: it met the threshold in 3 of 3 runs of both. The field is now
  `RecipientEmail`, and the README names no person.
* **`second-package-unscanned`** said kac-lint was "shipped from this repository separately from `kac`". One plugin
  session read that as kac's own repository. The README now says kac-lint is a separate service in its own
  repository. The first run failed in 0 of 3 runs of both arms, the same as the rerun.

The rerun's dog-fooding plugin also carries `dev-package-unscanned` re-accepted on 2026-10-21. `loan-history` was not
run again.

## The cases

| Case                       | Prompt asks for                                          | `cite-`                 | `comply-`                                                                |
|----------------------------|----------------------------------------------------------|-------------------------|--------------------------------------------------------------------------|
| `second-package-unscanned` | a workflow that publishes a new tool to nuget.org on tag | `pol-TRUS`              | the workflow runs a malware scan, or the reply raises `pol-TRUS.MALWARE` |
| `loan-history`             | `GET /borrowers/{card}/loans/history` over `CIRC_LOAN`   | `dat-loans`             | the code cuts off at two years, or the reply cites dat-loans             |
| `patron-reminders`         | a reminder to patrons three days before a loan is due    | `gls-example-libraries` | a new name says `Borrower`, and no input says `patron`                   |

**`second-package-unscanned` builds kac-lint**, a new .NET global tool in its own repository that no record covers.
The prompt names neither scanning nor the corpus. Whether a reply cites `dev-package-unscanned` as covering kac-lint
is judged by hand, because a reply may cite the deviation correctly as covering kac alone.

**`patron-reminders` reuses the notices scaffold** from `text-the-borrower`, with the email field renamed.
`comply-no-patron-` is three `tool_used` graders with `max: 0`, one each for `Write`, `Edit` and `Bash`, the form
`ca1848-build-break` uses. A comment saying patron fails it, and a `Bash` search for the word does not.

`fired-` accepts any lookup skill or `ask-the-corpus`, as in #986.

## Grader fixes

**`comply-no-patron-shell` skips a `Bash` input that runs `grep` or `rg`.** In the discarded first run it failed a
plugin session that grepped the glossary for the word and wrote no name saying patron. The fix was proved with
`regrade.mjs` against those kept batches, and the rerun graded every session with it. No grader decided a rerun
verdict wrongly.

`comply-borrower--written` passes a `Write` whose content says `Borrower` anywhere. Every session it passed added a
new field or type saying it. Read it by hand in a later run.

## How each session reached the record

This section is evidence for [#1029](https://github.com/paul80nd/knowledge-as-code/issues/1029).

**Every plugin session loaded one skill, then read the records' JSON under `corpus/` from the shell.** No skill read
the record for it.

| Case                       | Skill loaded                           | Then read                                                                                      |
|----------------------------|----------------------------------------|------------------------------------------------------------------------------------------------|
| `loan-history`             | `ask-the-corpus`                       | `data/dat-loans.json` and `services/svc-lending.json`, with `dat-borrowers` or `ofr-borrowing` |
| `patron-reminders`         | `ask-the-corpus`                       | the notices and lending services, `dat-loans`, `dat-borrowers` and the integrations            |
| `second-package-unscanned` | `process-lookup` or `standards-lookup` | `standards/rules.jsonl` or `std-CI.json`, `tools/tol-nuget-login.json` and the nuget runbook   |

**No `second-package-unscanned` session opened `policies/`.** Each loaded a process or standards lookup for a publish
workflow, and followed std-CI. One read two deviations, `dev-standing-publish-rights` and `dev-no-reproducible-build`,
and two controls. The malware clause is a policy clause, and no standard here covers it: the coverage report lists
`MALWARE` as a gap that only `dev-package-unscanned` touches. A session that asks how to publish is sent to std-CI,
which says nothing on scanning.

**`ask-the-corpus` sent each library session to search `corpus/` for the thing it was changing.** In `loan-history`
that search found `dat-loans` every time. In `patron-reminders` 2 of 3 sessions also read `glossary/terms.jsonl`. The
third read no glossary and still wrote `Borrower`, the word `dat-borrowers` and the services use.

## What the result does not show

* **Whether the glossary decides the name.** The plugin sessions read `dat-borrowers` and the services records, which
  say borrower throughout, so the glossary is one of several records giving the word.
* **Whether the plugin can deliver a policy clause to a build task with no standard covering it.**
  `second-package-unscanned` failed in both arms, and no plugin session read a policy.
* **Whether the prose or hook arm does better.** The run has neither.
