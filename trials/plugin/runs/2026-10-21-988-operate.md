# The #988 operate cases

**Two of the three payments scenarios met their threshold in the plugin arm and in no none run. The third met it in 1
of 3 plugin runs. The sandbox decided the other two cases, so they have no baseline.**

* `two-pending-amounts` met it in 3 of 3 plugin runs and 0 of 3 none runs. Every plugin session derived the key as
  `$"{orderId}:authorise"`, and every none session moved one `Guid.NewGuid()` out of the retry loop.
* `has-this-happened-before` met it in 3 of 3 plugin runs and 0 of 3 none runs. Every plugin reply cited `pmt-0002`
  and gave its cause. Every none reply found no record, and guessed a cause from the code.
* `unverified-fix` met it in 1 of 3 plugin runs and 0 of 3 none runs. Every plugin reply called `fix-0002` a draft or
  unverified, but two said so only after they had written the change.
* `golden-red-in-ci` and `notices-down` ran as a pilot only. In each, the trial sandbox blocks what the session needs,
  so each is listed in its folder's `excluded.tsv`.

The run gives each of the five `@proposed` scenarios in [`operate.feature`](../../use-cases/operate.feature) its case.
It writes the five cases [story #988](https://github.com/paul80nd/knowledge-as-code/issues/988) asks for, and runs
each in the plugin arm and the none arm.

## The excluded cases

**The sandbox decides `golden-red-in-ci` and `notices-down`**, so each is in its folder's `excluded.tsv`, and neither
ran past the pilot. Each needs something the export leaves out by design, and the sandbox blocks the fetch that
`corpus-retrieval` would make for it.

| Case               | What the export leaves out                                         | What the sandbox blocks                         |
|--------------------|--------------------------------------------------------------------|-------------------------------------------------|
| `golden-red-in-ci` | a runbook's steps: the export has `Symptoms` and `Impact` alone    | the fetch, and `dotnet`, on a mutex under `/tmp` |
| `notices-down`     | `owner`, which every type but deviations keeps out of its export  | the fetch                                       |

**`dotnet` cannot run in the sandbox.** Both golden sessions issued `GITHUB_ACTIONS=true dotnet run
tooling/kac-tests.cs` before their one edit, and the SDK failed to create a NuGet mutex under `/tmp`. Neither read a
diff, and neither passed `--update`. Each instead stopped `kac-tests.cs` passing `GITHUB_ACTIONS` to `kac`, which
rbk-goldens-disagree does not do.

**`golden-red-in-ci` may be a control.** The none session found `GITHUB_ACTIONS=true` from the code alone, because
`kac.cs` reads the variable. A capable engineer new to the repository might run the suite that way without the
runbook, so the case may not separate the arms even where `dotnet` runs.

**No plugin session can name `svc-notices`'s owner.** The plugin session read `svc-notices.json` and replied that no
record names whom to page. [Shaping a type](../../../docs/framework/shaping-a-type.md) keeps `owner` in the corpus,
because a reader holding a copy elsewhere cannot ask that person anything. The scenario asks for exactly that field.

## The cases

| Case                       | Prompt reports                                               | `cite-`                | `comply-`                                                 |
|----------------------------|--------------------------------------------------------------|------------------------|-----------------------------------------------------------|
| `two-pending-amounts`      | two pending amounts after a retried payment, and asks a fix  | `fix-0001`             | the new key derives from the order, as `{order}:`         |
| `has-this-happened-before` | two pending amounts, and asks whether it has happened before | `pmt-0002`             | the reply says a new key on each retry                    |
| `unverified-fix`           | refund breaks in the hour before midnight UTC                | `fix-0002`             | the reply says draft or unverified, its order read by hand |
| `golden-red-in-ci`         | a golden `FAIL` line in CI that passes locally               | `rbk-goldens-disagree` | a `Bash` call sets `GITHUB_ACTIONS=true`                  |
| `notices-down`             | overdue notices stopped, and asks whom to page               | `svc-notices`          | the reply names `mira.okonjo`                             |

**`two-pending-amounts` scaffolds a checkout** whose payment client retries a timed-out `POST /authorisations` with a
new `Guid.NewGuid()` key on each attempt. `comply-key--` has `Write`, `Edit` and `Bash` alternatives, each skipping a
`Bash` input that runs `grep` or `rg`.

**`has-this-happened-before` scaffolds the payment API**, which sends the PSP no key, so its code does not give the
cause away. **`unverified-fix` scaffolds the payment ledger**, whose reconciliation window cuts the day on
`Europe/London`. **`golden-red-in-ci` scaffolds a cut of this repository**: its last commit regenerated one golden
without `GITHUB_ACTIONS`, so the `::error` annotation line is missing from it. Its `flag-update` grader marks a run
that passed `--update`, and no score counts it. **`notices-down` reuses the notices scaffold** with an overdue sweep
added, and names no owner.

`fired-` accepts any lookup skill or `ask-the-corpus`, as in #986.

## Adjudication

Every session's workspace was read by hand against its trace. **Three `unverified-fix` verdicts were overturned:**

* **Plugin runs 2 and 3**, from pass to fail. Each wrote the UTC window first, and said `fix-0002` was unverified only
  in the reply that followed.
* **None run 3**, from pass to fail. `comply-unverified` matched "Not verified" over the session's own unbuilt change,
  and the session named no fix.

[Each corpus's `adjudication.tsv`](2026-10-21-988-operate/) gives the reason for every session.

## Grader fixes

No grader was changed between the pilot and the batch, so `merge.sh` combined them as they ran.

**`comply-unverified` now passes only where "unverified", "draft" or "not verified" is said of a fix or a record.** It
looks for one of those words within 300 characters after "fix" or "record" on the same line, or for "unverified" or
"draft" shortly before "fix". In the recorded run it matched "Not verified" over none run 3's own unbuilt change.
`regrade.mjs` proved the change against both payments batches. The new grader passes all three plugin replies and
fails all three none replies, none run 3 included, and the 87 unchanged verdicts agree with the tool. The grader still
reads the final reply, so the order stays a judgement made by hand. The recorded run is scored on its adjudication, and
the next run grades with the fix.

## How each session reached the record

This section is evidence for [#1029](https://github.com/paul80nd/knowledge-as-code/issues/1029).

**Every payments plugin session loaded `fix-lookup`, then read the records' JSON under `corpus/` from the shell.** No
skill read the record for it.

| Case                       | Skill loaded     | Then read                                                                              |
|----------------------------|------------------|----------------------------------------------------------------------------------------|
| `two-pending-amounts`      | `fix-lookup`     | `fixes/*.json`, then `std-IDEM` or the standards, and in 2 of 3 runs `postmortems/`    |
| `has-this-happened-before` | `fix-lookup`     | `fix-0001`, then `pmt-0002` and `pmt-0001` under `postmortems/`                         |
| `unverified-fix`           | `fix-lookup`     | `fix-0002`, found by a `grep` for midnight, then `std-RECON` or a `grep` of standards  |
| `golden-red-in-ci`         | `fix-lookup`     | `rbk-goldens-disagree.json`, found by a `grep` over `fixes/` and `runbooks/`           |
| `notices-down`             | `ask-the-corpus` | `svc-notices.json`, `itg-mail-delivery.json` and `itg-sms-notices.json`                |

**`has-this-happened-before` asked a question about a past incident, and each session loaded `fix-lookup`.** No
session loaded a skill for postmortems, because the payments plugin ships none. `fix-lookup` found `fix-0001`, and
each session then listed `postmortems/` from the shell and read `pmt-0002` there.

**`golden-red-in-ci`'s plugin session reached the runbook from `fix-lookup`**, by a `grep` that took in `runbooks/`.
No skill points at runbooks, and the session found only `Symptoms` and `Impact` there. It did not load
`corpus-retrieval`, and said it worked from the code because the steps had not come with the plugin.

## What the result does not show

* **Whether a session follows a runbook's steps in order.** `golden-red-in-ci` cannot measure it until the sandbox
  runs `dotnet` and allows the fetch, or the export includes the steps.
* **Whether the plugin can name a service's owner.** The export keeps `owner` out, so `notices-down` asks for a field
  the plugin does not have.
* **Whether a session waits for a person before it applies a draft fix.** No plugin session asked before it wrote the
  change.
* **Whether the prose or hook arm does better.** The run has neither.
