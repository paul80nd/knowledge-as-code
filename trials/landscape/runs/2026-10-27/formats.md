## 1. Open Knowledge Format (OKF)

### 1.1 The spec has moved, and kac links the frozen copy

The `okf/` folder of knowledge-catalog now says: "OKF now lives in its own repository:
GoogleCloudPlatform/open-knowledge-format." "Stop using the copy under `okf/` in this repository." "It is a frozen
snapshot, no longer maintained, and anything built against it will drift out of date."
([knowledge-catalog/okf](https://github.com/GoogleCloudPlatform/knowledge-catalog/tree/main/okf))

kac links that frozen copy in `.schema/reports.yaml` (lineage `prior-art`, line 23) and in
`docs/reference/export.md` (line 53). Both copies state version 0.2 and the same section list
([SPEC]; old copy), so nothing kac took has changed yet (inferred from comparing the two fetches; I did not diff them
byte for byte). The links should move to the new repository.

### 1.2 What OKF is, and for whom

* "OKF is a **universal, vendor-neutral format** for representing knowledge as plain markdown files with YAML
  frontmatter", "not tied to any particular agent, framework, model provider, or serving system." [OKF-README]
* Preamble: "It is designed to be authored by people, generated by agents, exchanged across organizations, and consumed
  by both." §1: "Increasingly, a knowledge corpus is not authored once and then read: it is continuously written and
  maintained by agents." [SPEC]
* Goals (§1) include "Standardize the small set of frontmatter fields that make an agent-maintained corpus" trustable,
  "without prescribing any runtime." Non-goals include "Defining a fixed taxonomy of concept types." and "Prescribing
  storage, serving, or query infrastructure." [SPEC]
* §1: "There is no schema registry, no central authority, and no required tooling." [SPEC]
* Its original home was a data catalog. knowledge-catalog's README describes Knowledge Catalog (formerly Dataplex) as a
  platform that "provides a dynamic knowledge graph of all your data", and the repository "features tools, agents, and
  samples that demonstrate Knowledge Catalog features." "This repository and its contents are not an official Google
  product." Apache-2.0. ([knowledge-catalog](https://github.com/GoogleCloudPlatform/knowledge-catalog)) The worked
  bundles are BigQuery datasets (ga4, stackoverflow, crypto_bitcoin, acme_retail) [OKF-README], so the subject is data
  assets, where kac's is engineering rules (inferred).

**Tooling it ships.** A Python reference agent, "a **proof of concept** demonstrating _one_ way to produce OKF bundles
automatically" [OKF-README]. `enrich` "writes one OKF doc per concept the source advertises, using BigQuery metadata
alone", then a web pass runs "the LLM as its own crawler" (Gemini, via `GEMINI_API_KEY` or Vertex AI). `visualize`
"renders any OKF bundle as a **self-contained interactive HTML file**". [OKF-README] A `connectors/` folder holds one
file, `gcp-knowledge-catalog.md`
([connectors](https://github.com/GoogleCloudPlatform/open-knowledge-format/tree/main/connectors)); I did not read it.
The README has no validator or conformance section; its only test content is `.venv/bin/pytest` [OKF-README]. No
release or tag exists, and `main` showed 6 commits ([repo](https://github.com/GoogleCloudPlatform/open-knowledge-format)).
knowledge-catalog's `toolbox/` holds "Metadata as Code" (metadata as "source code artifacts that can be sync'd") and an
Enrichment Agent; its README does not mention OKF ([toolbox](https://github.com/GoogleCloudPlatform/knowledge-catalog/tree/main/toolbox)).
None of its four `samples/` mentions OKF either ([samples](https://github.com/GoogleCloudPlatform/knowledge-catalog/tree/main/samples)).

### 1.3 Field by field: OKF against kac's universal fields

kac's universal fields are in `.schema/_universal.yaml`: `id`, `type`, `tier`, `status`, `owner` (required), `sources`,
`tags`, `accepts` (optional), with `title` and `allowTitleToDifferFromFilename` reserved for Azure DevOps.
`generated` and `verified` are not universal: `verified` is declared by `reports` and `fixes`, `generated` by
`reports` alone (`grep '^  generated:' .schema/*` returns `reports.yaml` only).

| OKF key (§) | OKF's wording [SPEC] | kac | Same / differs / absent |
|---|---|---|---|
| Concept ID (§2) | "The path of the concept's file within the bundle, with the `.md` suffix removed." No `id` field. | `id`, required: "Stable, unique across the corpus, never reused". `metadata.md`: "You may correct a filename. You may not correct an id." | **Differs, on purpose.** OKF's identity moves when a file moves; kac's does not. |
| `type` (§4.1) | Required, the only always-required key: "A short string identifying the kind of concept." Consumers tolerate unknown values. | `type`, required, "checked against the folder", and must name a type the corpus has a schema for. | **Same name**, kac stricter: a closed set, each with a schema. |
| `title` (§4.1) | Recommended. "Human-readable display name. If omitted, consumers MAY derive a title from the filename." | Not a field: "`title` ... It is the H1, verbatim" (`metadata.md`). Reserved and ignored for ADO. | **Absent in kac** by design; kac derives from the H1, OKF from the filename. |
| `description` (§4.1) | Recommended. "A single sentence summarizing the concept." | No universal or per-type field of that name (grep of `.schema/`). | **Absent in kac.** |
| `resource` (§4.1) | Recommended. "A URI that uniquely identifies the underlying asset the concept describes." | No such top-level field. Per-type link fields such as `applies-to` point at service records, not URIs. | **Absent in kac.** |
| `tags` (§4.1) | Recommended. "A YAML list of short strings for cross-cutting categorization." | `tags`, optional, pattern `^[a-z0-9-]+$`. | **Same name**, kac constrains the alphabet. |
| `sources` (§5.1) | "`sources` records the materials a concept derives from, external or internal to the bundle." | `sources`, optional (required on reports). | **Same name and meaning.** |
| `sources[].resource` | "REQUIRED within an entry." "Names either a concrete artifact a consumer can follow" "or a population or scope descriptor it cannot." | `resource`, required: "An address a reader can follow, a path inside the corpus, or the population it was drawn from." | **Same**, both forms kept. |

Per-claim attribution is the notable loss. |
| `sources[].title`, `.author`, `.last_modified` | "Human-readable label for the source." / "Who or what produced the source, in the actor convention (§7)." / "When the source itself last changed." | Left out (same note). | **Absent in kac**, stated. |
| `sources[].usage_count`, `usage_window` | "How often `resource` was exercised ... over `usage_window`"; `usage_window` is "Written once as a sibling of `sources`" with "a `{ from, to }` datetime range." | Absent. | **Absent in kac**; fits OKF's data-asset subject more than kac's (inferred). |
| — | OKF puts no version on a source. | Reports add `sources[].version`, required: "The `content-version` that corpus was at." | **kac addition**, stated in `reports.yaml` divergence. |
| `generated` (§5.2) | "`generated` records how the current content was produced." `by`: "REQUIRED within `generated`. An actor (§7)." `at`: "An ISO 8601 datetime marking the content's last meaningful change." | Reports only. `at` (timestamp) and `by` required, plus kac's own `report` and `tool`. | **Same keys**, kac narrower in reach (one type) and adds two keys. |
| `verified` (§5.2) | "`verified` records who or what has confirmed the content against its sources or `resource`." "Multiple entries capture independent checks". "`verified` is independent of `generated.at`: content can change without re-confirmation." "A single verifier MAY be written as one `{ by, at }` mapping without the list dash." "Consumers MUST treat a bare mapping as a one-element list." | Reports and fixes. `required-when: 'status != draft'`; one entry per actor (`one-verification-per-actor`); reports refuse the `generated.by` actor (`no-self-verification`). | **Same name and keys.** kac stricter in three ways (stated in `reports.yaml`). See 1.5 for two departures kac does not state. |
| Trust tiers (§5.3) | "No `verified` key ⇒ **unverified**." "`verified` by non-`human:` actors only ⇒ **machine-confirmed**." "`verified` by a `human:<id>` actor ⇒ **human-reviewed**." "Trust tiers are advisory signals, not access control." | Exported as `trust` (`docs/reference/export.md`). | **Same three tiers.** kac stores the derived tier in its export, where OKF derives it at read time. |
| `status` (§5.4) | "`draft`: not yet reviewed; possibly incomplete." "`stable`: default; ready for consumption." "`deprecated`: kept for links and history; no longer current." "Absent `status` ⇒ `stable`." | Required; values per type, each naming its `in-force:` value. Reports take `draft`, `active`, `stale`. | **Same name, differs.** kac has no default and no shared vocabulary; OKF's `stable` default is the opposite of kac's required field. |
| `stale_after` (§5.5) | "An absolute instant." Reports read staleness from `content-version`. | **Different name**, date not instant, and a review prompt rather than a staleness verdict (inferred). Reports diverge on purpose (stated). |
| Actors (§7) | "`<producer>/<version>` for agents and tools", "`human:<id>` for a person", "`process:<id>` for an automated process". | — | No owner field. | `owner`, required. | **kac addition.** |
| — | No trust class by kind of knowledge. | `tier`, required (`decided`, `normative`, `descriptive`, `procedural`). | **kac addition.** |
| — | Unknown keys: "Producers MAY include any additional keys." "Consumers SHOULD preserve unknown keys when round-tripping and MUST NOT reject documents with unrecognized fields." | kac rejects keys a type does not declare (key-order and schema checks). | **Opposite stance.** A kac record is an OKF concept; an OKF concept is mostly not a valid kac record (inferred). |
| `okf_version` (§8) | "Bundles MAY declare the version they target with `okf_version: "0.2"`" in a bundle-root `index.md`. | No format version in records; `.corpus.yaml` carries `content-version`; each type's `export.version`. | **Differs**: kac versions the content and the export shape, OKF versions the format. |
| `index.md` (§8) | "MAY appear in any directory". Purpose: "letting a human or agent see what is available before opening individual documents." "Producers MAY generate `index.md` automatically". | `kac generate` writes indexes into type pages, and `validate` checks the generated-block markers. | **Same idea**, kac enforces freshness (`generate --check`). |
| `log.md` (§9) | "a flat list of date-grouped entries, newest first". "Date headings MUST use ISO 8601 `YYYY-MM-DD` form." | No per-folder log. Records carry changelogs, which "run newest-first" (memory note; only standards check it). Git holds history: `created`/`updated` are "Git knows" (`metadata.md`). | **Absent as a file**; kac relies on git. |
| Attested computations (§10) | A concept type with `runtime` (required), `parameters`, `computation`, `executor`, `attester`. Controls record what checks a rule but carry no runnable check. | **Absent in kac.** |

### 1.4 Cross-references, link checking, and versioning of the format

* **OKF tolerates broken links, by rule.** "Consumers MUST tolerate broken links: a link whose target does not exist in
  the bundle is not malformed." Link kinds are prose: "A link from concept A to concept B asserts a *relationship*."
  "The specific kind (parent/child, references, joins-with, depends-on) is conveyed by the surrounding prose."
  Bundle-relative links are "the **recommended** form because it is stable when documents are moved within their
  subdirectory." [SPEC]
* **kac fails them.** A broken link is an error (`link-resolves`, `README.md`); typed reference fields resolve to a
  record of the named type; `reciprocal:` pairs must agree; part citations such as `pol-VURM.TIMEBOX` must resolve
  (`docs/framework/metadata.md`, `docs/maintaining/validation.md`). This is where kac is furthest ahead: relationship
  kinds are fields, not prose, and the graph is checked.
* **Conformance.** OKF: "Every frontmatter block contains a non-empty `type` field." Consumers "MUST NOT reject a
  bundle" for missing optional fields, unknown types or keys, broken links or missing `index.md`. "Consumers SHOULD
  treat all other constraints as soft guidance." [SPEC] OKF is a tolerant interchange format; kac is a strict
  authoring discipline (inferred).
* **Format versioning.** "This document specifies OKF version **0.2**." "Revisions are versioned as `<major>.<minor>`".
  "A **minor** version bump introduces backward-compatible additions"; "A **major** version bump may make breaking
  changes (renaming required fields, changing reserved filenames)." Yet "v0.2 supersedes OKF v0.1 and is a minor
  version bump under §12, except for two deliberate breaking changes" (`timestamp` → `generated.at`, `# Citations` →
  `sources`). [SPEC] So OKF broke its own §12 rule in its one release. kac versions content (`content-version`), the
  export shape per type (`export.version`), and the tool (semver on nuget.org); it has no version for the record format
  as a whole (inferred from `docs/reference/export.md` and `README.md`).

### 1.5 Where kac's OKF borrowing departs without saying so

1. **Verifications older than `generated.at` are dropped.** `docs/reference/export.md`: "A verification taken before
   `generated.at` is left out." OKF: "`verified` is independent of `generated.at`: content can change without
   re-confirmation." [SPEC] kac's tier therefore differs from the one OKF would derive from the same frontmatter, and
   the page then says "The three tiers are the Open Knowledge Format's." The `reports.yaml` divergence does not list
   this. It may be a deliberate improvement, but it is an unstated one.
2. **"agents alone" drops a qualifier.** kac's export table says `machine-confirmed` when `verified` contains "agents
   alone", and `docs/use/cli/report.md` line 90 says "agents alone are machine-confirmed". OKF says "non-`human:`
   actors only", which includes `process:<id>`. kac admits `process:` in `verified.by`, so a `process:`-only record
   is presumably machine-confirmed in code too, but the wording says otherwise (inferred; I did not read the C#).
3. **Bare mapping.** OKF lets a single verifier be a bare `{ by, at }` and says consumers "MUST treat a bare mapping as
   a one-element list." kac declares `verified` as `type: list`, and a list field "refuses a scalar" (memory note), so
   kac likely rejects the bare form (inferred, not tested). Strictness is kac's right as a producer; as a consumer of
   OKF it would be non-conformant.

### 1.6 How OKF reaches an agent

By being plain files: "An engineer can `cat` a concept; an LLM can ingest it verbatim into context." Generated
`index.md` files "let an agent or human navigate the hierarchy one level at a time." [OKF-README] No MCP server, skill
or plugin is described. The reference agent writes bundles; it does not serve them [OKF-README]. kac goes further: an
export with per-section fidelity plus a Claude Code plugin with lookup skills (`README.md`, `docs/reference/export.md`).

### 1.7 Same / differs / lacks

**Same.** Markdown with YAML frontmatter in a directory tree; `type`, `tags`, `sources[].resource`, `verified[{by,at}]`,
`generated{by,at}`, the three actor forms and the three trust tiers; generated indexes for progressive disclosure.

**Differs.** Identity (path vs immutable `id`); `status` (fixed three with a default vs per-type, required); staleness
(`stale_after` instant vs `review-by` date and `content-version`); unknown keys (preserve vs reject); broken links
(tolerated vs fatal); `title` (field vs H1); format version (`okf_version` vs content and export versions); scope
(any knowledge, any type, no schema registry vs a closed, schema'd taxonomy).

**What kac lacks that OKF has.**

* `description`: a one-sentence summary per record. kac's export ships summaries per section, but no record-level
  sentence (inferred from the field lists in `.schema/*.yaml`). A lookup or build index would use it.
* Per-claim attribution: `sources[].id` joined to Markdown footnotes. kac's `sources` can say where a record came from
  but not which sentence came from which source.
* `generated` and `verified` on every type. kac has them on two types; OKF makes them available to every concept.
* `resource`: a URI for the asset described. kac points at its own service records instead.
* `log.md`: a human-readable change history per folder, independent of git.
* Attested computations: a sanctioned, verifiable runnable check. The nearest kac idea is a control, which names what
  checks a rule but carries nothing runnable.
* Interop stance: a consumer rule that tolerates and preserves unknown keys, so a bundle round-trips through tools.
* A viewer: `visualize` renders a bundle as a self-contained graph page.

**Where kac is ahead.** Immutable ids and part addresses (`pol-VURM.TIMEBOX`); a schema per type, enforced in CI;
typed, reciprocal, resolved relationships where OKF leaves the kind to prose and tolerates dangling links; `owner` and
`tier`; stricter verification (required past draft, one per actor, no self-verification); a versioned export contract;
delivery to an agent as a plugin. OKF has no validator at all [OKF-README].

## 2. Validators for Markdown with frontmatter

None of these has typed, resolved cross-references checked in CI as kac does. Astro comes closest.

### 2.1 Astro content collections

* **What.** Collections are "defined in a special `src/content.config.ts` file" with `defineCollection()`; each takes a
  `loader` (`glob()`, `file()`) and an optional Zod `schema`. "If any file violates its collection schema, Astro will
  provide a helpful error to let you know." [ASTRO] Whether that fails the build is not stated on the page.
* **Ids.** "every content entry `id` is automatically generated in a URL-friendly format based on the content
  filename", overridable by a `slug` property. [ASTRO] Path-derived, like OKF; not kac's immutable id.
* **Cross-references.** `reference()` lets "you ... define a property in a collection schema as an entry from another
  collection." [ASTRO] But "Validation of referenced entries happens at runtime when using `getEntry()` or
  `getEntries()`", and "if a referenced entry is invalid, the array will contain undefined". [ASTRO-REF] So a dangling
  reference is the page author's runtime problem, not a build failure (inferred from that wording). No reciprocal
  check, no part addressing.
* **Editors.** "Astro auto-generates JSON Schema files for collections", output to `.astro/collections/`. [ASTRO]
* **Agents.** Not addressed for collections. [ASTRO]
* **Versus kac.** Same: typed collections, schema per collection, typed reference fields. Differs: schema in TypeScript
  code, references checked at render time, part of a site generator. Lacks (kac): editor JSON Schema generated from the
  type schema, giving autocomplete and red squiggles while writing. Ahead (kac): build-time reference resolution,
  reciprocity, part citations, schema in YAML a corpus owns, no site framework needed.

### 2.2 remark-lint-frontmatter-schema

* **What.** "Validate Markdown frontmatter YAML against an associated JSON schema", using Ajv. [RLFS] The settings docs
  say "draft-2019-09" while linking Ajv's draft-07 docs [RLFS], so the draft is unclear.
* **Association.** A `'$schema'` key in the frontmatter, or a `schemas` glob mapping in the remark config; the local key
  wins. [RLFS]
* **CI and editors.** Runs as `remark .` or through ESLint MDX; VS Code via `unifiedjs.vscode-remark`. No CI recipe
  beyond a passing mention. [RLFS]
* **Cross-references.** Schemas may `$ref` other schema files; nothing says it checks references between documents.
  [RLFS]
* **Status.** ISC licence, 81 stars, no releases shown on the page. [RLFS]
* **Versus kac.** Same: per-file frontmatter schema in CI. Lacks (kac): a standard schema language (JSON Schema) with
  ecosystem tooling, and per-file `$schema` pointing. Ahead (kac): everything beyond one file's frontmatter: body
  sections, parts, ids, cross-record references.

### 2.3 Vale (prose) and markdownlint (structure), briefly

* **Vale.** "Vale is a command-line tool that brings code-like linting to prose." It "focuses (primarily) on the style
  of writing rather than its grammatical correctness." Rules are YAML naming an `extends` extension point;
  `level: error` "will cause CI builds to fail". [VALE] A `meta` scope collects "A document's machine-readable
  content—an anchor name, an image's file name" (v3.18.0 or later) [VALE-SCOPES]; I could not establish whether Vale
  lints frontmatter. Styles travel as packages: "A package is a style, a configuration file, or both, published as an
  archive", installed by `vale sync`. [VALE-PKG]
  **Versus kac.** Complementary, not competing. kac checks modals in bold on rules and Y-statement bounds, but has no
  general prose linter. kac's writing rules live in skills (`technical-writing`), which a person or agent applies, not
  a CI check. **Lacks (kac):** mechanical enforcement of house prose style, and a package mechanism for sharing a style.
  A corpus could run Vale alongside `kac validate` (inferred).
* **markdownlint.** Structural Markdown rules grouped by tag (headings, links, whitespace, code, table); front matter
  is ignored by default via `options.frontMatter`; custom rules are supported. [MDL] MD051 "Link fragments should be
  valid" checks fragments "for headings in the document" [MD051]; cross-file links appear unchecked (inferred from
  that wording). **Versus kac:** kac checks cross-file links and anchors, which markdownlint does not; markdownlint
  covers Markdown hygiene kac leaves alone.

## 3. What this means for kac

1. **Repoint the OKF links.** kac cites a copy its owner calls "a frozen snapshot, no longer maintained". The canonical
   spec is <https://github.com/GoogleCloudPlatform/open-knowledge-format/blob/main/SPEC.md>.
2. **State, or undo, two departures from OKF's trust tiers** (section 1.5): dropping verifications older than
   `generated.at`, and "agents alone" where OKF says "non-`human:` actors only". The export page claims OKF's tiers
   while computing a different one.
3. **Candidates to borrow, each needing a reader first** (per the repository's "two primary sources" habit):
   a record-level `description`; `sources[].id` with footnote attribution; `generated`/`verified` beyond reports and
   fixes; editor JSON Schema generated from `.schema/` (Astro's move). Attested computations are the most novel idea in
   the family and map onto controls, but are out of scope for v1 (inferred).
4. **The comparison page can claim** that neither OKF nor any validator reviewed resolves typed cross-references at
   build time; OKF forbids rejecting on a broken link, and Astro defers it to runtime.
