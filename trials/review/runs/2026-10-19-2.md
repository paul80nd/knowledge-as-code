Each session was read twice: the subagent's report, which is the `Skill` result in `trace.jsonl`, and the final reply.
The reply is the result.

**The missing commit**, case by case:

|----:|--------|-------|----------------------------------------------------------------------------------------------------------------------------|
|   1 | fail   | fail  | Neither mentions the commit. The report's one `std-DEPLOY` rule is the one on configuration, and the reply has none.       |

**No control checks `std-DEPLOY`.** Run 2's report and reply list it, and say nothing automated checks any finding.
Run 3's reply adds the rule without saying what checks it. Run 1 never reaches the rule.

**The SHOULD departure.** All three reports filed the London timestamp as a judgement call, citing
`std-OBS.one-request-reads-as-one-timeline` and quoting the reason. All three replies cited the rule and the reason,
and called the departure allowed. The `judgement-` grader passed one: the other two say "is fine" and "a SHOULD
allows". Run 3's report and reply also filed a MUST under the same rule as a violation, because a request with no
`traceparent` logs a null trace id. That obligation is a different one, and the finding is sound.

**The secret in the added lines.** All three reports opened `## Violations` on
`std-SECRET.nowhere-else-holds-a-secret`, quoting the obligation and the line. All three replies cited that id and put
the key first among the fixes, under headings of their own: "Fix before opening the PR", "Standards findings", and a
numbered list. None kept the word Violations.

The scenario's Then asked for the finding to be filed under Violations, and the reply writes its own headings, so the
Then graded the session's layout. After the run it was reworded to: cites `std-SECRET` and reports it as a change to
make before merging. Read against that wording, all three replies pass: each cites the rule and puts removing the key
ahead of opening the pull request. That reading is adjudication of a Then written afterwards, and the strict score
above stands as the run's result.

## What the reviews show

* **Claude Code's main session writes its own reply from a forked skill's report.** Every report opened on the relay
  line, and every session wrote its own reply. A line in the report does not change that, so the trial grades the
  reply the person reads, and reads the report beside it.
* **The replies kept more ids.** Every reply cited a rule id for each standards finding it kept, bar one shortened to
  `std-GATES...`. In the first run, 2 of 3 `should-departure` replies cited none.
* **A MUST the change adds is found every time.** The hard-coded key was the first finding in all six texts.
* **A MUST the change inherits is found by chance.** One report in three connected the change to `std-DEPLOY`'s
  artefact rule, against none in the first run, and it filed the rule as a gap in the pipeline. In run 3 the main
  session looked the rule up itself after the review.
